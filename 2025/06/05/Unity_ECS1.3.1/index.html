Unity ECS 核心数据概念详解

RefRW<T> 与 RefRO<T>：安全的数据访问引用

RefRW<T> 和 RefRO<T> 是 Unity ECS 1.0+ 中用于在 SystemAPI 查询和组件获取时，安全访问组件数据的特殊结构体。它们的核心作用是明确数据访问意图（读写或只读）并自动处理作业系统 (Job System) 的依赖关系。

RefRW<T> (ReadWrite Reference)

  • 作用：提供对组件数据 T 的读写引用。

  • 用途：当需要在系统中修改组件的数据时使用（如更新位置、减少生命值）。

  • 访问数据：通过其 .ValueRW 属性。

  • 依赖管理：自动声明对组件类型 T 的写依赖，帮助 Job System 防止数据竞争。

RefRO<T> (ReadOnly Reference)

  • 作用：提供对组件数据 T 的只读引用。

  • 用途：当只需要读取组件数据而不需要修改它时使用（如碰撞检测、根据速度计算方向）。

  • 访问数据：通过其 .ValueRO 属性。

  • 依赖管理：自动声明对组件类型 T 的读依赖。允许多个系统并发读取。

选择原则：

  • 最小权限原则：仅在需要修改时使用 RefRW<T>，否则使用 RefRO<T>。
  • 性能与并行性：RefRO<T> 有利于 Job System 的并行化。
  • Burst 编译器友好：两者都有助于 Burst 生成优化代码。
  • 明确性：显式使用 RefRW 和 RefRO 是最佳实践。

DynamicBuffer<T>：动态元素集合

DynamicBuffer<T> 用于表示实体上动态大小的元素集合。T 必须是一个实现了 IBufferElementData 接口的 struct。

  • 作用：允许一个实体关联一个可变长度的同类型数据元素列表。

  • 用途示例：路径点 (Waypoint)、攻击目标列表 (TargetEntity)、状态效果 (StatusEffect)。

  • 特性：

    • 动态大小：可运行时添加/移除元素。
    • 值类型元素：T 必须是 struct。
    • 类列表 API：
      • Add(T element)
      • Insert(int index, T element)
      • RemoveAt(int index)
      • Clear()
      • Length (属性)
      • IsEmpty (属性)
      • this[int index] (索引器，读写)
      • AsNativeArray(): 转换为 NativeArray<T>。
      • Reinterpret<U>(): 重新解释为另一种 IBufferElementData 类型。
    • 内存管理：由 ECS 系统管理，数据存储在 Chunk 中或独立的非托管内存块。

  • 获取与使用：

    • 通过 SystemAPI.GetBuffer<T>(Entity entity) 获取。

    • 在 SystemAPI.Query 中：

  • 依赖管理：获取 DynamicBuffer<T> 时，默认声明对该缓冲区组件类型的读写依赖。

ECS 中的其他重要数据类型/概念

1. Entity

  • 轻量级 struct，包含 Index 和 Version。
  • 实体的唯一标识符。
  • Entity.Null 表示无效实体。

2. IComponentData

  • 接口，用于定义包含单个、固定大小数据实例的组件。
  • 通常是 struct，不应包含托管类型引用。
  • 示例：Position { float3 Value; }, Health { float Current; }
  • 每个实体最多拥有一个该类型的组件实例。
  • 通过 SystemAPI.GetComponent<T>(), GetComponentRO<T>(), GetComponentRW<T>() 访问。

3. IBufferElementData

  • 接口，用于定义构成 DynamicBuffer<T> 中元素类型的数据结构。
  • 必须是 struct，不应包含托管类型引用。
  • 示例：Waypoint { float3 Position; float WaitTime; }

4. IAspect

  • 一种更高级的抽象，将相关的组件（IComponentData, DynamicBuffer）及访问逻辑封装到 readonly struct 中。

  • 可直接在 SystemAPI.Query 中查询。

  • 内部使用 RefRW 和 RefRO 定义对组件的访问权限。

  • 简化复杂实体原型的操作。

5. ISharedComponentData (共享组件)

  • 用于存储在多个实体之间共享的数据。
  • 实体根据其共享组件的值进行分组到不同的 Chunks。
  • 值必须是可比较的 (struct 实现 IEquatable<T>)。
  • 不应频繁改变，因为改变会导致实体移动 Chunk (昂贵操作)。
  • 用途：渲染设置 (RenderMesh)、队伍 ID、静态配置。
  • 访问：EntityManager.GetSharedComponent<T>(), EntityManager.SetSharedComponent<T>()。
  • 查询筛选：WithSharedComponentFilter<T>()。

6. IEnableableComponent (可启用组件)

  • 允许组件被动态地“启用”或“禁用”，而无需实际添加/移除。
  • 禁用时，查询默认忽略，除非明确指定包含。
  • SystemAPI 提供 SetComponentEnabled<T>(), IsComponentEnabled<T>() 等。
  • 查询：WithDisabled<T>(), WithEnabledUP<T>()。
  • 组件需实现空接口 IEnableableComponent。

7. Chunk 组件 (IComponentData on Chunks)

  • 组件数据可以附加到 Chunk 本身，而非单个实体。
  • 该组件的数据对于 Chunk 内所有实体都是相同的。
  • 用途：存储 Chunk 范围内的元数据或状态。
  • 访问：EntityManager.GetChunkComponentData<T>(ArchetypeChunk) 或在 IJobChunk 中。

8. Singleton Components (单例组件)

  • 标记一个组件类型，使其在整个 World 中最多只有一个实例（即只有一个实体拥有该组件）。
  • 用途：全局配置、系统状态、事件触发器。
  • 访问：SystemAPI.GetSingleton<T>(), SetSingleton<T>(), GetSingletonRW<T>() 等。

9. EntityQuery

  • SystemAPI.Query<...>() 的底层结果（通常不直接操作进行迭代）。
  • 定义了一组筛选条件，用于匹配具有特定组件组合的实体。
  • 可从中获取实体数组、组件数据数组、ArchetypeChunk 等。

10. ArchetypeChunk

  • 内存中实际存储实体及其组件数据的基本单位。
  • 一个 Chunk 包含相同原型 (Archetype，即组件类型组合相同) 的实体。
  • 在 IJobChunk 作业中直接操作。

Unity: NativeArray<T> 详解

NativeArray<T> 是 Unity C# Job System 和 Burst Compiler 技术栈中的一个核心数据结构。它是一个非托管内存数组，提供了对一段连续内存块的类型安全访问，并且设计用于在多线程作业 (Jobs) 之间安全高效地共享数据。

核心特性与作用

  1. 非托管内存 (Unmanaged Memory):

    • NativeArray<T> 的数据存储在 C# 托管堆之外的原生内存 (Native Memory) 中。
    • 优点:
      • 避免垃圾回收 (GC) 开销: 由于数据不在托管堆上，创建、销毁和访问 NativeArray 不会触发 GC，这对于追求高性能和流畅帧率的应用至关重要。
      • 与原生代码互操作: 可以轻松地将 NativeArray 的指针传递给 C/C++ 等原生代码库。
      • Burst Compiler 友好: Burst Compiler 可以直接操作原生内存，生成高度优化的机器码。

  2. 类型安全 (Type Safety):

    • 尽管是原生内存，NativeArray<T> 仍然是类型安全的。T 必须是一个**非托管类型 (Unmanaged Type)**，这意味着：
      • T 必须是 struct (值类型)。
      • T 不能包含任何引用类型 (如 string, class 对象) 或指向托管对象的指针。它可以包含其他非托管结构体或基本类型 (int, float, bool, Entity, float3 等)。

  3. 固定大小 (Fixed Size):

    • NativeArray<T> 在创建时需要指定大小，并且其大小在生命周期内不能改变。如果需要动态大小的集合，应考虑使用 NativeList<T> (类似于 List<T>) 或 ECS 中的 DynamicBuffer<T>。

  4. 与 Job System 紧密集成:

    • NativeArray<T> 是 Job System 中传递和操作数据的主要方式之一。
    • 作业数据共享: 作业可以安全地读取或写入传递给它们的 NativeArray。
    • 安全性: Job System 会通过**安全系统 (Safety System)**（在编辑器和开发构建中默认开启）来跟踪 NativeArray 的使用情况，防止常见的并发问题：
      • 竞态条件 (Race Conditions): 例如，一个作业正在写入 NativeArray，而另一个作业同时在读取或写入它，没有适当的同步。
      • 悬垂指针/越界访问: 访问已释放的 NativeArray 或超出其边界的索引。
      • 别名问题: 安全系统有助于检测不安全的内存别名。
    • 只读标记: 可以通过 [ReadOnly] 属性或 AsReadOnly() 方法将 NativeArray 标记为只读传递给作业，这允许 Job System 进行更积极的并行调度。

  5. 显式的内存管理 (Explicit Memory Management):

    • NativeArray<T> 需要手动分配和释放内存。
    • 分配: 使用构造函数 new NativeArray<T>(int length, Allocator allocatorLabel, NativeArrayOptions options = NativeArrayOptions.ClearMemory)。
      • length: 数组的元素数量。
      • allocatorLabel: 指定内存分配的类型和生命周期，常见的有：
        • Allocator.Temp: 最短生命周期，通常用于单帧内的临时数据，必须在同一帧内释放。分配速度快。
        • Allocator.TempJob: 生命周期比 Temp 稍长，可以跨越几帧（通常是 4 帧），专为短期作业设计。
        • Allocator.Persistent: 长生命周期，可以持续整个应用程序的运行时间，直到手动释放。分配和释放较慢。
    • 释放: 必须调用 Dispose() 方法来释放原生内存。
    • 未释放的内存会导致内存泄漏！ Unity 的安全系统会在编辑器中警告未释放的 NativeArray。

  6. Blittable 类型:

    • 由于 T 必须是非托管类型，NativeArray<T> 中的数据通常是 “blittable” 的，这意味着它们在托管内存和原生内存中的表示是相同的，可以直接进行内存拷贝，非常高效。

Unity 数据容器与 Job System 在非 ECS 架构中的应用

数据容器对比: DynamicBuffer<T>, NativeArray<T>, NativeList<T>

这三者都是 Unity DOTS 技术栈中处理数据的核心容器，但它们各有特点和适用场景。

NativeArray<T> (回顾)

  • 核心：固定大小的非托管数组。
  • 优点：性能高，GC-free，与 Job System 和 Burst 结合紧密。
  • 缺点：大小固定，需要手动管理内存。
  • 用途：作业的主要输入输出，当数据量已知或可预测时非常高效。

NativeList<T>

  • 核心：动态大小的非托管列表，类似于托管的 List<T>，但使用原生内存。
  • 优点：GC-free，可以动态添加和删除元素。
  • 缺点：
    • 需要手动管理内存 (Dispose())。
    • 频繁地动态调整大小（特别是添加超出当前容量的元素）可能会导致内存重新分配和拷贝，带来性能开销。
    • 在 Job 中直接修改 NativeList 的结构（添加/删除元素）通常是不安全的或不推荐的，因为这会使长度和容量信息在多线程环境下变得不可靠。通常的做法是：
      1. 在主线程填充 NativeList。
      2. 将其（或其 AsArray() 视图）传递给 Job 进行只读处理，或者让 Job 将结果写入另一个 NativeArray 或 NativeList (并行 Job 通常写入 NativeArray 的特定索引，或使用 NativeQueue.ParallelWriter 等并发容器)。
      3. 如果 Job 需要动态输出，可以考虑 NativeQueue 或 NativeStream。
  • API 亮点:
    • Capacity: 当前分配的内部数组大小。
    • Length: 实际存储的元素数量。
    • Add(T item): 添加元素，如果 Length == Capacity，会触发扩容。
    • AddRange(NativeArray<T> array): 高效添加 NativeArray 的内容。
    • AsArray(): 返回一个 NativeArray<T> 视图，指向 NativeList 内部的已填充数据部分 (从索引 0 到 Length-1)。这个视图共享内存，但其长度是固定的。
  • 用途：当需要在主线程构建一个大小不确定的列表，然后传递给 Job 进行处理，或者 Job 的输出大小不确定但可以在 Job 完成后一次性收集时。

Unity ECS: SystemBase 与 World 详解

在 Unity ECS (Entity Component System) 中，SystemBase 和 World 是两个核心概念，它们共同构成了 ECS 架构的基础。

SystemBase

SystemBase 是一个抽象基类，用于创建在主线程上运行的 ECS 系统。虽然 ECS 1.0+ 版本更推荐使用 ISystem 接口 (通常是 partial struct 实现) 以获得更好的 Burst 编译支持和更轻量级的结构，但 SystemBase 仍然在某些场景下有用，或者在一些较早的 ECS 项目中会遇到。

作用:

  • 提供一个面向对象的基类来封装系统的逻辑。
  • 允许系统持有托管数据和状态 (相比之下，ISystem (struct) 通常不直接持有复杂的托管状态)。
  • 提供了方便的属性和方法来与 EntityManager、World 和时间等进行交互。
  • 支持传统的 C# 事件和委托。

生命周期方法 (主要重写的方法):

  1. OnCreate():

    • 在系统第一次被创建并添加到 World 时调用一次。
    • 适合进行一次性的初始化操作，例如：
      • 获取和缓存其他系统的引用。
      • 创建和缓存 EntityQuery 对象 (用于后续查询实体)。
      • 订阅事件。
      • 检查必要的单例组件是否存在 (RequireSingletonForUpdate<T>())。

  2. OnStartRunning():

    • 当系统从禁用状态变为启用状态，或者在 OnCreate() 之后首次准备运行时调用。
    • 当系统之前因为 RequireSingletonForUpdate<T>() 缺失单例而未运行时，一旦单例出现，此方法会被调用。
    • 适合进行那些依赖于其他系统或数据已经准备就绪的设置。

  3. OnUpdate():

    • 每帧调用一次（如果系统是启用的并且其更新条件满足）。
    • 这是系统执行其核心逻辑的地方，例如：
      • 查询实体。
      • 读取和修改组件数据。
      • 创建或销毁实体。
      • 与其他系统交互。

  4. OnStopRunning():

    • 当系统从启用状态变为禁用状态时调用，或者在 OnDestroy() 之前。
    • 当系统因为 RequireSingletonForUpdate<T>() 所需的单例消失而停止运行时，此方法会被调用。
    • 适合进行清理那些在 OnStartRunning() 中设置的资源或状态。

  5. OnDestroy():

    • 当系统从 World 中被移除或 World 被销毁时调用一次。
    • 适合进行最终的清理工作，例如：
      • 释放非托管资源。
      • 取消事件订阅。

常用属性和方法:

  • EntityManager (属性):

    • 获取当前 World 的 EntityManager 实例。
    • 用于执行所有与实体和组件相关的底层操作（创建/销毁实体，添加/移除组件，设置/获取组件数据等）。
    • 示例: EntityManager.CreateEntity(), EntityManager.AddComponentData(entity, new Position { Value = float3.zero })。

  • World (属性):

    • 获取当前系统所属的 World 对象。

  • Time (属性):

    • 获取一个 TimeData 结构体，包含 DeltaTime、ElapsedTime 等时间信息，与 SystemAPI.Time 类似。

  • Enabled (属性):

    • 获取或设置系统是否启用。禁用的系统不会执行 OnUpdate()。

  • Entities (属性，用于 ForEach 查询):

    • 提供一个流畅的 API (Entities.ForEach) 来迭代符合特定条件的实体和组件。这是 SystemBase 中一个非常核心的查询方式。
    • 示例:
    • Entities.ForEach 可以与 .Schedule() (单线程 Job), .ScheduleParallel() (多线程 Job), 或 .Run() (主线程立即执行) 结合使用。
    • 它会自动处理依赖关系。

  • GetEntityQuery(params ComponentType[] componentTypes) / GetEntityQuery(EntityQueryDesc queryDesc):

    • 创建或获取一个 EntityQuery 对象。EntityQuery 是更底层的查询机制，可以用于获取组件数据的 NativeArray，或用于 IJobChunk。
    • 通常在 OnCreate() 中创建并缓存。

  • RequireForUpdate<T>() / RequireSingletonForUpdate<T>():

    • 在 OnCreate() 中调用，用于声明系统运行的先决条件。
    • RequireForUpdate<T>(): 要求存在至少一个实体拥有组件 T 或存在 T 类型的 EntityQuery (如果 T 是 EntityQueryOptions 或 ComponentType)，系统才会运行。
    • RequireSingletonForUpdate<T>(): 要求存在类型为 T 的单例组件，系统才会运行。如果单例不存在，系统将不会执行 OnUpdate()，直到单例出现。

  • GetSingleton<T>() / SetSingleton<T>(T value):

    • 获取或设置单例组件的值。

  • HasSingleton<T>():

    • 检查是否存在类型为 T 的单例组件。

  • Dependency (属性):

    • 用于管理 Job System 的依赖关系。Entities.ForEach(...).Schedule() 或 ScheduleParallel() 会返回一个 JobHandle，通常应该赋值给 Dependency，以确保 Job 正确完成并与其他系统的 Job 同步。
    • this.Dependency = jobHandle;

与 ISystem 的对比:

  • ISystem 是 struct，更轻量，更适合 Burst，是现代 ECS 的首选。
  • SystemBase 是 class，允许托管状态，更像传统的 Unity 脚本，但可能不完全 Burst 兼容，且有对象分配开销。
  • ISystem 使用 SystemAPI 进行交互，而 SystemBase 有自己的成员属性和方法。

World

World 是 ECS 中最顶层的容器对象。一个 Unity 应用程序可以有多个 World 实例。

作用:

  • 包含实体、组件和系统: 每个 World 都有其自己独立的 EntityManager (管理实体和组件) 和一组系统 (处理逻辑)。
  • 隔离数据和逻辑: 不同的 World 之间的数据和系统是隔离的。这对于实现不同的模拟状态（如客户端世界、服务器世界）、编辑器工具世界或特定功能（如烘焙世界）非常有用。
  • 管理系统的生命周期和更新循环: World 负责创建、初始化、更新和销毁其内部的系统。它有一个默认的系统更新循环。
  • 时间管理: 每个 World 可以有自己独立的时间流 (World.Time)。

常用属性和功能:

  1. EntityManager (属性):

    • 获取该 World 实例的 EntityManager。这是与实体和组件交互的主要入口。

  2. Systems (属性):

    • 一个只读列表，包含此 World 中的所有系统 (ComponentSystemBase 类型的列表)。

  3. Time (属性):

    • 获取该 World 的 TimeData，包含 DeltaTime, ElapsedTime 等。

  4. Name (属性):

    • 获取或设置 World 的名称，方便调试和识别。

  5. Flags (属性):

    • 获取或设置 WorldFlags。这些标志可以被 [WorldSystemFilter] 用来决定系统是否应该在这个世界中创建。
    • 示例: world.Flags = WorldFlags.Game; 或 world.Flags |= WorldFlags.Baking;

  6. DefaultGameObjectInjectionWorld (静态属性):

    • 获取或设置默认的、用于 GameObject 注入 (Hybrid ECS 场景) 的世界。通常是主游戏世界。

  7. All (静态属性):

    • 一个只读列表，包含当前应用程序中存在的所有 World 实例。

  8. 构造函数 new World(string name, WorldFlags flags = WorldFlags.None):

    • 创建一个新的 World 实例。

  9. Dispose():

    • 销毁 World 及其所有系统和实体。必须手动调用以释放资源。

  10. GetOrCreateSystem<T>() / GetOrCreateSystem(Type type):

    • 获取 World 中已存在的 T 类型系统，如果不存在则创建并添加一个新的实例。
    • 示例: var mySystem = World.DefaultGameObjectInjectionWorld.GetOrCreateSystem<MyMovementSystem>();

  11. DestroySystem(ComponentSystemBase system) / DestroySystem<T>():

    • 从 World 中移除并销毁指定的系统。

  12. GetExistingSystem<T>() / GetExistingSystem(Type type):

    • 获取 World 中已存在的 T 类型系统，如果不存在则返回 null。

  13. Update():

    • 手动触发该 World 中所有可更新系统的更新循环。通常由 Unity 的播放循环自动调用默认世界的 Update()。对于自定义世界，你可能需要手动调用。

  14. GetExistingSystemManaged<T>() / GetOrCreateSystemManaged<T>():

    • 针对托管系统（继承自 ComponentSystemBase 而非 SystemBase 的较旧系统，或是一些特殊的 Unity 系统）的类似方法。

如何获取 World:

  • 在 SystemBase 或 ISystem (通过 SystemState) 中:
    • SystemBase: this.World
    • ISystem: ref SystemState state 参数，state.World
    • SystemAPI: SystemAPI.World (获取当前上下文的 World)
  • 通过静态属性: World.DefaultGameObjectInjectionWorld
  • 通过 World.All 列表: 遍历并根据名称或标志查找。

使用多个 World 的场景:

  • 客户端/服务器: 在同一进程中模拟客户端和服务器，各自拥有独立的 World。
  • 编辑器工具: 创建一个临时的 World 来处理编辑器下的数据转换或预览。
  • 内容烘焙: 如前所述，烘焙过程通常在专门的烘焙 World 中进行。
  • 模拟不同状态: 例如，一个用于“实时游戏”，另一个用于“回放”或“计划模式”。

总结:

  • SystemBase 提供了一个传统的面向对象方式来构建主线程系统，并提供了方便的 API (尤其是 Entities.ForEach) 来与 ECS 数据交互。尽管 ISystem 更受推崇，但 SystemBase 仍有其用武之地。
  • World 是 ECS 的核心容器，管理着独立的实体、组件和系统集合。它使得数据和逻辑的隔离成为可能，并驱动着系统的生命周期和更新。

理解 SystemBase（或其现代替代品 ISystem）如何在其所属的 World 上下文中运作，是掌握 Unity ECS 的关键。
